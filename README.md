# 石油ローリー配車エージェント

油槽所から需要家（GS・運送会社営業所）への**二次配送**を組み、外の変化に応じて
自分で組み直すエージェント。第5回 Agentic AI Hackathon with Google Cloud 応募作品。

舞台は麻里布油槽所（岩国・和木）の配送圏。西は出光徳山、東は水島製油所、
山陰は境港油槽所との境まで。

---

## 何を解くのか

配車係が毎朝やっていることは、次を同時に満たす組み合わせを見つける仕事である。

1. **槽への製品割当と槽容量** — 槽1つに1油種。混ぜられない
2. **需要家の受入時間枠と受入可能量** — 運送会社営業所は朝の出庫前しか受けない
3. **乗務員の資格と拘束時間** — 改善基準告示（拘束13時間、運転9時間、連続4時間で休憩30分）
4. **タンク在庫の発注点** — 割ったら必ず今日行く
5. **油槽所の積込回数と回転**

ここに、寒波（灯油需要が跳ねる）、値上げ発表（駆け込み需要）、乗務員の欠勤、
道路の工事や事故が乗る。1つ動くと全部が動く。

## 設計の中心にある一線

> **AIは何を計算させるか決める。計算は Python がする。**

| 層 | 担当 | 中身 |
|---|---|---|
| 決定論コア（`core/`） | 数字を出す | OR-Tools CP-SAT による配車最適化。所要時間、積載量、到着時刻、拘束時間 |
| エージェント層（`app/`、W4で拡張） | 何を見るか・いつ組み直すか・どう説明するか | 診断面談、外部シグナルの翻訳、再計画トリガー、理由説明、手直しの取り込み |

散文と数字が食い違う事故は、モデルに算術をさせたときにしか起きない。
`core/` はモデルを1行も呼ばない。

## 同じ入力なら、同じ計画が返る（条件つき）

審査員が手元で再現できること、そして計画品質の回帰テストが成立することは、
同じ要件から来ている。乱数種を固定するだけでは足りなかった。

同点の最適解が複数あると、目的値は同じまま**どの車がどの需要家をどの順で回るか**が
実行のたびに変わる。実際に、同じ要求を2回投げて別の割当が返ってきた。
対策として、求解を2段階に分けている（`core/solver.py`）。

1. **1段目** — 主目的（走行時間・拘束時間・未訪問の罰・車両の固定費）を最小化
2. **2段目** — 主目的を1段目の値に固定し、タイブレークだけを最小化

タイブレークは3段。重みの形にそれぞれ理由がある。

| | 基準 | 重み | なぜその形か |
|---|---|---|---|
| 1 | 到着時刻の合計 | — | 着けるうちに着く。M2 で確率的な所要時間を入れたとき時間枠を割りにくい |
| 2 | 便と需要家の組 | `(u+1)·i²` | `u·100+i` のような加法分離型では、2軒を2便の間で入れ替えても総和が変わらない |
| 3 | 回る順序 | `i²·j` | 経路は閉じた輪なので、`i+j` や `i·j` では一周した総和が順序で変わらない |

**この保証が効くのは、両段が最適性を証明できたときだけ。** 時間切れで
打ち切った解には同じ保証がない。その区別は握りつぶさず、
`diagnostics.reproducible` として計画自身に持たせてある。

複数便を入れる前（1台1日1便）は、10通りの seed をそれぞれ3回解いて、
割当・順序・時刻まで完全に一致することを確認済み。複数便では既定の60秒で
5件中4件が証明できる水準で、ここを全件にするのが次の課題（下記）。

## 動かす

```bash
python -m venv .venv
.venv/Scripts/python.exe -m pip install -r requirements-dev.txt
```

配車を1日ぶん組んで、配車係の言葉で読む:

```bash
.venv/Scripts/python.exe -m scripts.plan_day --verbose
```

季節・乱数種・欠勤を変える:

```bash
.venv/Scripts/python.exe -m scripts.plan_day --season summer --seed 7 --absent d1
```

API を立てる:

```bash
.venv/Scripts/python.exe -m uvicorn app.main:app --reload --port 8080
```

| 経路 | 用途 |
|---|---|
| `GET /api/healthz` | 生存確認。設定とコスト台帳のバックエンドを返す |
| `POST /api/plan` | 当日の配車を組む |
| `GET /api/scenario` | 需要側だけを見る（どこが切迫しているか） |
| `GET /api/usage` | その日のコスト使用状況と上限 |

テスト:

```bash
.venv/Scripts/python.exe -m pytest
```

## 暴走対策

エージェントを外に出す以上、URLを知った誰かが叩き続けるだけで請求が伸びる。
三層で守る（`app/ledger.py`）。

1. **1リクエストの上限** — 1回の再計画が青天井に膨らまない
2. **利用者ごとの1日上限** — 一人が使いすぎない
3. **全体の1日上限** — 何人来ても請求が青天井にならない最後の砦

3 が本命。2 だけだと識別子を変えれば素通りする。
`/api/healthz` が台帳のバックエンドを返すのは、**本番で `memory` になっていたら
全体上限が効いていない**から。画面に出す前にここで気づく。

## データについて

需要家の座標・タンク容量・消費量・受入時間枠はすべて**合成データ**であり、
実在の事業所の実績値ではない（`core/generator.py`）。

地理は合成していない。「岩国から浜田まで灯油を運ぶと拘束時間が厳しい」という
制約の効き方は、実際の距離でないと成立しない。作り物の座標で作った問題は、
作り物の制約しか生まない。

### いま分かっている限界

**1. 複数便にしたぶん求解が重い。** 5通りの seed を60秒で解いた実測:

| 1台あたりの便数 | 最適性を証明 | 求解時間 | 回れる軒数 | 切れかけで残る軒 |
|---|---|---|---|---|
| 1便まで | 5/5 | 0.8〜4.8秒 | 7〜8 | 1〜4 |
| **2便まで（既定）** | 4/5 | 21〜56秒 | 8〜12 | 1〜2 |
| 3便まで | 0/5 | 60秒で打ち切り | 8〜12 | 1〜2 |

1台1日1便は現場の姿ではないうえ、全車が午前中に帰庫して以降ずっと空くのに
切れかけの需要家が残っていた。2便までを既定にしたのはこの実測による。
3便まで広げても計画は良くならず、探索が広がったぶんを取り返せていない。

上限を上げる前にモデル側の高速化が要る。次に試すのは、便ごとに circuit を
張るのをやめ、**油槽所の節点を複製して1台1周回にまとめる**やり方。
5台×3便で15本の輪を張っている今の形が、そのまま探索の重さになっている。

**2. 単槽のまま。** 油種を区別せず量の合計だけで解いている。多槽に上げたときに
「多槽にしたせいで解けなくなった」のか「元から解けていなかった」のかを
切り分けられるよう、単槽の解を基準線として残してある。

**3. 連続運転の休憩を、挟む位置まで決めていない。** 1日の運転時間が4時間の
区切りを越えるごとに30分の余裕を拘束時間の中に確保する、という近似。
向きは安全側（余裕を先に取る）なので、実際に挟んでも計画は破れない。
