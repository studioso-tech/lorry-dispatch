# 石油ローリー配車エージェント

油槽所から需要家（GS・運送会社営業所）への**二次配送**を組み、外の変化に応じて
自分で組み直すエージェント。第5回 Agentic AI Hackathon with Google Cloud 応募作品。

舞台は麻里布油槽所（岩国・和木）の配送圏。西は出光徳山、東は水島製油所、
山陰は境港油槽所との境まで。

---

## 何を解くのか

配車係が毎朝やっていることは、次を同時に満たす組み合わせを見つける仕事である。

1. **槽への製品割当と槽容量** — 槽1つに1油種。混ぜられない
2. **需要家の受入時間枠と受入可能量** — 運送会社営業所は朝の出庫前しか受けない
3. **乗務員の資格と拘束時間** — 改善基準告示（拘束13時間、運転9時間、連続4時間で30分の中断）
   **＋ 労働基準法34条の休憩**（労働8時間超で1時間）。両者は足さず、大きいほうを取る
4. **タンク在庫の発注点** — 割ったら必ず今日行く
5. **油槽所の積込回数と回転**

ここに、寒波（灯油需要が跳ねる）、値上げ発表（駆け込み需要）、乗務員の欠勤、
道路の工事や事故が乗る。1つ動くと全部が動く。

これらの数字がどこから来ていて、どこまで裏が取れているかは
[docs/業務前提.md](docs/業務前提.md) にまとめてある。法令／実務／仮置の3区分で
出どころを明示してあり、**仮置のまま残している項目もある**。

## 設計の中心にある一線

> **AIは何を計算させるか決める。計算は Python がする。**

| 層 | 担当 | 中身 |
|---|---|---|
| 決定論コア（`core/`） | 数字を出す | OR-Tools CP-SAT による配車最適化。所要時間、積載量、到着時刻、拘束時間 |
| エージェント層（`app/`、W4で拡張） | 何を見るか・いつ組み直すか・どう説明するか | 診断面談、外部シグナルの翻訳、再計画トリガー、理由説明、手直しの取り込み |

散文と数字が食い違う事故は、モデルに算術をさせたときにしか起きない。
`core/` はモデルを1行も呼ばない。

## 同じ入力なら、同じ計画が返る

審査員が手元で再現できること、そして計画品質の回帰テストが成立することは、
同じ要件から来ている。乱数種を固定するだけでは足りなかった。**2つの壁**があった。

### 壁1: 同点の最適解

同点の最適解が複数あると、目的値は同じまま**どの車がどの需要家をどの順で回るか**が
実行のたびに変わる。実際に、同じ要求を2回投げて別の割当が返ってきた。
対策として、求解を2段階に分けている（`core/solver.py`）。

1. **1段目** — 主目的（走行時間・拘束時間・未訪問の罰・車両の固定費）を最小化
2. **2段目** — 主目的を1段目の値に固定し、タイブレークだけを最小化

タイブレークは2段で、下の段が上の段を打ち消せないよう桁を分けてある。

| | 基準 | 重み | なぜその形か |
|---|---|---|---|
| 1 | 到着時刻（需要家ごとに重み付け） | `(i+1)·到着` | 単純な合計では、2軒の訪問順を入れ替えても総和が同じになる日があった |
| 2 | 車と需要家の組 | `(v+1)·(i+1)²` | `v·100+i` のような加法分離型では、2軒を2台の間で入れ替えても総和が変わらない |

### 壁2: 実時間で打ち切ると、機械が違えば答えが違う

複数便を入れてから、最適性を証明できる日とできない日に**両極に割れた**。
解ける日は数秒、解けない日は90秒かけても解けず、制限時間を60秒から150秒に
延ばしても改善しなかった。そして証明できるかどうかは**マシンの速さで決まる**。
並列数を落としただけで、手元で再現できた日が崩れて別の計画が返った。

**実時間で打ち切る限り、審査員のマシンで同じ計画は出ない。**

解決は、打ち切りを実時間から**探索の量**（CP-SAT の決定的時間）に変えること。
同じ量だけ探索すれば、どのマシンでも同じ場所で止まる。**最適性を証明できない日
でも、同じ計画が返る**（2回解いて、計画・目的値・タイブレーク値まで一致）。

ただし**決定性と時間の上限は両立しない。** 「念のため」実時間の上限も併置したら、
同じマシンの2回の実行で別の計画が返った。実時間の側が探索に干渉するため。

**並列探索も決定性を壊した。** 最初は8本の並列探索に決定的な並列化
（`interleave_search`）を付けていたが、重い日（需要95kL、現実の2倍を載せた
試験の日）で、同じ入力から**目的値は同じで中身の違う計画**が返った。軽い日に
一致していたのは、最適解がほぼ1つに絞られていたからにすぎなかった。
**再現モードは単スレッド**で解く。別プロセスで2回解いてタイブレーク値まで
一致し、主目的の値も並列8本と同じだった（計画の質は落ちない）。

両立させる必要は無かった。**用途が2つある。**

| モード | 打ち切り | 再現性 | 使う場面 |
|---|---|---|---|
| `reproducible` | 探索の量（上限なし） | 保証する | 審査員の検証・回帰テスト。**API の既定** |
| `fast` | 実時間 | 両段が最適性を証明できたときだけ | 当日の組み直し・体制設計の掃引 |

当日の組み直しは「いま組み直してほしい」要求なので時間で切るのが正しく、
再現性は検証のためのものなので時間を犠牲にしてよい。**同じ設定で両方を
まかなおうとしていたのが誤り**だった。

計画は再現できる根拠を自分で申告する（`diagnostics`）:

| キー | 値 |
|---|---|
| `reproducible` | 真偽 |
| `reproducible_basis` | `deterministic_search`（探索量で打ち切った）／`proven_optimal`（両段が最適性を証明した）／`null` |
| `ortools_version` | **これが違えば、同じ入力でも別の計画になりうる** |
| `workers_used` | 同上。再現モードは vCPU 数に関係なく1（単スレッド） |

再現モードの所要時間（5台・冬・1週間）は **0〜14秒**。現実の需要の日は、
探索量の上限に届く前に最適性の証明まで終わる。重い試験の日では5〜6分かかる
（単スレッドの代償）。遅いマシンでは延びるが、**計画は変わらない**。

## 動かす

```bash
python -m venv .venv
.venv/Scripts/python.exe -m pip install -r requirements-dev.txt
```

配車を1日ぶん組んで、配車係の言葉で読む（再現モード。1〜2分かかることがある）:

```bash
.venv/Scripts/python.exe -m scripts.plan_day --verbose
```

急ぐときは実時間で打ち切る（再現は保証しない）:

```bash
.venv/Scripts/python.exe -m scripts.plan_day --fast --time-limit 30
```

季節・乱数種・欠勤を変える:

```bash
.venv/Scripts/python.exe -m scripts.plan_day --season summer --seed 7 --absent d1
```

見込みより売れた先を足す（連休・寒波。`c02:2` は全油種を見込みの2日ぶん、
`c02:kerosene:1.5` は灯油だけ1.5日ぶん）:

```bash
.venv/Scripts/python.exe -m scripts.plan_day --date 2026-10-16 --sold-more c02:regular:2
```

API を立てる:

```bash
.venv/Scripts/python.exe -m uvicorn app.main:app --reload --port 8080
```

| 経路 | 用途 |
|---|---|
| `GET /api/healthz` | 生存確認。設定とコスト台帳のバックエンドを返す |
| `POST /api/plan` | 当日の配車を組む。`mode` は `reproducible`（既定）か `fast`。朝から分かっていた事象は `sold_more` |
| `POST /api/replan` | 当日の発注（発注システムかFAX）を差し込んで組み直す。日中に分かった事象は `sold_more_now` |
| `POST /api/intake/fax` | FAX画像を読み、読めたら組み直す（Gemini は写すだけ） |
| `POST /api/intake/note` | 配車係のメモを読む。電話の連絡は予告として試算だけ |
| `POST /api/return` | 持ち戻りへの手を優先順に出す |
| `GET /api/escapes` | 直近30日の逃げ道と、恒常化の恐れ |
| `GET /api/scenario` | 需要側だけを見る（どこが切迫しているか） |
| `GET /api/usage` | その日のコスト使用状況と上限 |

画面は `/` にある（`app/static/`、素の HTML/CSS/JS。外の CDN は使わない）。
三つのタブ——今日の配車・当日の差し込み・持ち戻り——で、上の API をそのまま叩く。
**画面では計算しない。** 数字は API が出したものを描くだけで、kL への換算だけが例外。

## 合言葉

公開URLで触ってもらうときだけ、`DEMO_KEY` を置く。置くと `/api/` の口が
合言葉を求める（`/api/healthz` と画面そのものは素通し）。

```bash
DEMO_KEY=合言葉 .venv/Scripts/python.exe -m uvicorn app.main:app --port 8080
```

渡し方は**リンク1本**。`?k=` は画面が憶えてURLから消すので、以後は付けなくてよい。

```
https://<サービスのURL>/?k=合言葉
```

curl では `-H "X-Demo-Key: 合言葉"` か `?k=` を付ける。

これは秘密ではない（URLと一緒に文字で渡す）。止めたいのは**URLを拾った誰かの
連打**であって、本気の相手ではない。支出そのものを止めるのは次の台帳の上限である。

テスト（約15分）:

```bash
.venv/Scripts/python.exe -m pytest
```

数分かかる検証（最適性を証明できない日の再現性など）。提出前とソルバーを触ったあとに回す:

```bash
.venv/Scripts/python.exe -m pytest -m slow
```

## 暴走対策

エージェントを外に出す以上、URLを知った誰かが叩き続けるだけで請求が伸びる。
三層で守る（`app/ledger.py`）。

1. **1リクエストの上限** — 1回の再計画が青天井に膨らまない
2. **利用者ごとの1日上限** — 一人が使いすぎない
3. **全体の1日上限** — 何人来ても請求が青天井にならない最後の砦

3 が本命。2 だけだと識別子を変えれば素通りする。
`/api/healthz` が台帳のバックエンドを返すのは、**本番で `memory` になっていたら
全体上限が効いていない**から。画面に出す前にここで気づく。

## データについて

需要家の座標・タンク容量・消費量・受入時間枠はすべて**合成データ**であり、
実在の事業所の実績値ではない（`core/generator.py`）。

地理は合成していない。「岩国から浜田まで灯油を運ぶと拘束時間が厳しい」という
制約の効き方は、実際の距離でないと成立しない。作り物の座標で作った問題は、
作り物の制約しか生まない。

### いま分かっている限界

**1. 求解がまだ重い。** 便ごとに輪を張るのをやめ、油槽所の節点を複製して
1台1周回にまとめたことで、1段目（主目的の最小化）は 20〜45秒 → 5〜15秒に
なった。5通りの seed で目的値・便数・軒数がすべて変更前と一致しており、
モデルとしては等価である。

**支配項は2段目（タイブレークの最小化）に移った。** 15〜40秒かかる。
2段目を速くする試みは3つとも失敗した（`core/solver.py` の冒頭に記録してある）。
最も危なかったのは、決定性の条件を緩めて **`reproducible` が真を返しながら
計画が違う**状態を作ったこと。フラグが嘘をつくくらいなら遅いほうがよい、
という判断で元に戻した。

現状、5通りの seed のうち4件が完全に決定的。残る1件は1段目が時間切れで、
`reproducible=False` と正しく申告している。

体制設計の掃引（500回超の求解）を成立させるには、あと一桁速くする必要がある。
掃引ではコストと実行可能性しか要らないので、`tiebreak_phase=False` で2段目を
丸ごと省ける（実装済み）。

**2. 車両と乗務員が1対1で固定されている。** 実際の石油ローリーは乗務員を
交代して24時間動く。いまの実装は車の稼働上限が人の拘束上限と同じになっており、
**車を遊ばせている**。次の作業で分離する。

**3. 受入枠を営業形態から導いている。** 実際に夜間の荷卸しができるかどうかは、
営業時間ではなく**無人荷卸し設備の有無**で決まる。ここも作り直す。

**4. 単槽のまま。** 油種を区別せず量の合計だけで解いている。多槽に上げたときに
「多槽にしたせいで解けなくなった」のか「元から解けていなかった」のかを
切り分けられるよう、単槽の解を基準線として残してある。

**5. 連続運転の休憩を、挟む位置まで決めていない。** 1日の運転時間が4時間の
区切りを越えるごとに30分の余裕を拘束時間の中に確保する、という近似。
向きは安全側（余裕を先に取る）なので、実際に挟んでも計画は破れない。

**6. 休息期間が入っていない。** 前日の帰庫から翌日の出庫までの間隔を見て
いないので、19:00帰庫の翌日04:00出庫（休息9時間）を平気で出す。
